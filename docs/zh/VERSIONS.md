# 我们盯哪几个版本（中文原文）

Google 发着 **67 个 NDK 版本**（15 个大版本，r16…r30）和 **82 个 build-tools
版本**。这个矩阵追不过来，所以判据必须写下来 —— 否则「盯哪个」就会悄悄变成
「谁最后看的那天哪个最新」。

## 判据

**盯生态在钉的，不是盯最新的。**

- **三个 LTS**：Google 只给五个 NDK 标过 LTS（r21e、r23、r25、r26、r27），
  我们跟最近三个：**r25、r26、r27**。
- **加一个「当前默认」**：AGP 和主流框架默认用的那个，今天是 **r28** ——
  **不是最新的 r30**。
- **每个大版本只留一个补丁版**，留哪个看下面。

只按「新」选是错的：r29、r30 都在，但几乎没人用；而 r28 是所有**不写
`ndkVersion`** 的工程从 AGP 9.3 那儿拿到的那个。

## 留哪个补丁版，以及为什么不总是最新的

工程里钉的是**精确版本号**，所以补丁版的选择要紧：

| 谁 | 钉的精确版本 | 是哪个 | 是该代最新吗 |
|---|---|---|---|
| React Native | `27.1.12297006` | r27**b** | **不是** —— 最新是 27.3.13750724（r27d） |
| Flutter、AGP 9.3 默认 | `28.2.13676358` | r28**c** | 是 |
| Godot（master） | `29.0.14206865` | r29 最新 | 是 |

所以「只留最新补丁版」会把 `27.1.12297006` 丢掉 —— 那样**每个 React Native 工程
都得手改 `ndkVersion`**。不改的话，AGP 会去下他们钉的那个版本，而那是 x86_64 的。
2026-08-31 实测：完全不钉的情况下，AGP 9.3.2 **一声不响装了 2.2 GB 的 x86_64
NDK**，它的 clang 在 ARM64 上根本 exec 不了。

所以：**每个大版本留一个，留的是生态在钉的那个。**

## 现状

| 大版本 | 我们编的 | 为什么 | 编了吗 |
|---|---|---|---|
| r27（LTS） | `27.1.12297006` | 当前 LTS；React Native 钉它 | **是** |
| r28 | `28.2.13676358` | AGP 9.3 默认；Flutter 钉它 | **编了** |
| r26（LTS） | `26.3.11579264` | 老 LTS，按需 | 否 |
| r25（LTS） | `25.2.9519653` | 老 LTS，按需 | 否 |

r28 的包：`android-ndk-28.2.13676358-linux-aarch64-ours.tar.gz`，341 MB，
sha256 `7c8a609de5c93ffaa2d8f3df59083123c24a16a3295f4867792fab8668f4b383`。

`build-tools` 是另一回事：我们的二进制来自 AOSP 源码、**跟 build-tools 版本号
没有内在关系**，所以 `tools/install.sh --build-tools <版本>` 能覆盖 **82 个中的
任意一个** —— 取那个版本的官方文件，把我们的铺上去。

## 多支持一个版本要花什么

约 **88 分钟 LLVM 编译**（实测，4 核 ARM64）、一个 **349 MB** 的包、一整轮验收。
四个 NDK 版本 ≈ 每次发版六小时机器时间、1.4 GB 产物。

## 怎么加

```bash
tools/build-ndk-version.sh 28.2.13676358                  # 或 --ndk /路径
tools/build-ndk-version.sh --ndk /路径 --dry-run           # 只推导不编
```

它读目标 NDK 自己的 `AndroidVersion.txt`（里面写着 clang 版本和
`rXXXXXX<字母>`），推出 LLVM 分支名，**并去上游确认那个分支真的存在**才开始编。
拿 r27.1 校准过：推出来的三个值跟仓库里写死的一字不差。

编的时候还会反向交叉验证：NDK 的 `clang_source_info.md` 声明了它那份 clang 的
上游基点，那个提交必须出现在我们编译所用的 LLVM 树里 —— 否则就会发出一个
「戳着它并非编自那个版本」的编译器。

**老版本**：`patches/ndk/` 是照 r27 的构建脚本写的，**在 r28 上验过能打**。
r25/r26 是 2022–2023 年的，还没试。

## r28 那份带一个补丁位的版本偏差

我们给 r28 编的 clang 自报 **19.0.2**，而 NDK 声明 **19.0.1**。两者都来自 Google 的
`llvm-r530567` 分支 —— 我们编分支 tip，而 Google 切出 r28c 之后分支又往前走了。
（r27 那次严丝合缝是**运气**：tip 恰好还停在发布点。）

要编就得显式 `ALLOW_CLANG_VER_SKEW=1`，默认是**响亮地失败** —— 一个悄悄戳错版本的
编译器，正是这个仓库不肯发的东西。

这个偏差实测意味着什么（2026-09-01）：

- clang 的资源目录按**大版本**命名（`lib/clang/19`），所以把 r28c 的运行时嫁接到
  我们 19.0.2 的编译器上，路径是对得上的；
- `ndk-build` 和 CMake toolchain 两条路都编得出能用的 aarch64 `.so`；
- 用它编的 APK **在真机上跑起来了**（Android 16 / arm64-v8a）：
  `RESULT native ok: 64-bit … 20+22=42`，而且从设备上拉回来的 APK 跟本地那份
  **sha256 完全一致**；
- 产物 `.so` 的 `.comment` 里**同时有** `clang version 19.0.1` 和 `19.0.2` ——
  我们编译器生成的代码，链着 NDK 自带的运行时件。

有一步在这台机器上做不了：**驱动行为的黄金对照**（`build-llvm.sh` 3/6）是照
clang 18.0.2 录的，而 clang 19 展开 AArch64 target-feature 的方式变了。
录一份 clang 19 的黄金值需要能执行官方 x86_64 clang 的机器。那一步现在对别的版本
**明说「没验」而不是判失败** —— 没测不等于坏了，也不等于没事。
